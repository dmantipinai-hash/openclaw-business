# OpenClaw: Развёртывание в закрытом контуре (Air-gap Enterprise)

> Агент работает **только внутри контура**, без доступа к внешнему интернету.

---

## 1. Модель — локальная или в контуре

OpenClaw по умолчанию звонит к провайдерам (OpenAI, z.ai и т.д.). Для закрытого контура:

- **Ollama** (локальная модель на сервере) — самый простой вариант
- **vLLM / LocalAI** — если есть GPU-сервер в контуре
- Модель должна быть доступна по **внутреннему URL**
- Много агентов → vLLM с балансировщиком, одного Ollama не хватит

---

## 2. Инструменты — запретить внешние вызовы

### Отключить или ограничить:
- `web_search` → отключить или заменить на внутренний поисковик
- `web_fetch` → ограничить whitelist доменов контура
- Все cron задачи с `agentTurn` → не должны звать наружу
- Skills, которые ходят в интернет (ClawHub, GitHub и т.д.) → отключить

### Ограничение Git до определённых репозиториев:
- Подменить `baseUrl` на внутренний **GitLab/Gitea**
- Через `tools.alsoAllow` разрешить только конкретные методы
- MCP-сервер для Git с wrapper-обёрткой
- Агент работает только с разрешёнными репозиториями, не с全网 GitHub

### Песочница для исполнения кода:
- **Crabbox** (внутренний компонент OpenClaw) для изоляции
- Агент пишет скрипты → исполняются в sandbox

---

## 3. NPM зависимости — оффлайн установка

- Node-модули предзагрузить: **verdaccio** / npm cache / tarball
- OpenClaw использует **pnpm** → `pnpm fetch` для создания оффлайн-кеша
- Кеш упаковывается в Docker-слой
- Обновления оффлайн (флешка / внутренний registry)

---

## 4. Docker / Deploy

- Dockerfile — собрать образ и перенести в контур
- **Harbor** — внутренний Docker Registry
  - Сканирование уязвимостей через **Trivy**
- `render.yaml` — для облачного деплоя (неактуален в контуре)

---

## 5. Каналы — только внутренние

- ❌ WhatsApp / Telegram / Signal → недоступны из контура
- ✅ WebChat (браузер)
- ✅ Matrix (если развёрнут в контуре)
- ✅ Mattermost / Slack (если внутренние)

---

## 6. Проверка — агент действительно не ходит наружу

- **Network policy / firewall** на уровне ОС (разрешить только внутренние IP)
- Прокси с whitelist
- OpenClaw может пытаться звонить к API — перехватывать
- **Сертификаты:** в контуре свои CA → `NODE_EXTRA_CA_CERTS` в Node.js, иначе агент не достучится до внутренних HTTPS

---

## 7. Аудит и логирование

- Кто что спросил, что агент ответил — логи не уходят наружу
- **Audit Trail:** включить `control-plane-audit.ts`
- Все вызовы инструментов (кто, когда, параметры) → **ELK / Grafana Loki**

---

## 8. Авторизация и доступы (Identity)

### Trusted Proxy Auth:
- OpenClaw не знает пароли сотрудников
- **Keycloak / Authentik / Nginx+Authelia** — проверяет Kerberos/LDAP
- Передаёт пользователя в OpenClaw через заголовок `X-Forwarded-User`
- Конфиг: `gateway.auth.mode: "trusted-proxy"`

### RBAC (ролевая модель):
- Бухгалтерия → инструмент "1С-отчёты"
- Разработчики → "GitLab-API"
- Через систему политик OpenClaw (`role-policy.ts`)

---

## 9. Безопасность данных (DLP)

- Агент может "слить" секреты из одной системы в другую (зарплатная ведомость → общий чат)
- **Message Hooks** — DLP-фильтр на исходящие сообщения
- Паттерны: номера карт, гриф "Секретно", персональные данные → блокировка до модерации

---

## 10. Интеграция с внутренними системами

### 1С / SAP:
- **OpenAPI MCP server** — скармливаешь `swagger.json` внутренней системы → агент автоматически учится с ней работать

### Active Directory:
- Read-only LDAP доступ → агент отвечает "Кто отвечает за проект X?", "Найди почту начальника отдела"

---

## 11. Резервное копирование и отказоустойчивость

- **Postgres** — для логов и сессий (критично для длинных диалогов)
- **Redis** — кеш промптов
- Бэкапы Postgres → внутри контура

---

## 12. RAG — база знаний организации

- Внутренние регламенты, PDF, Wiki → векторная БД
- **Milvus** или **Qdrant** развёрнутые в контуре
- Агент отвечает на вопросы по внутренним документам

## 13. Архитектура делегатов (Delegate Architecture)

Вместо модели «личного помощника» — чёткое разделение ответственности между агентами.

### Трёхуровневая система доступа:

| Уровень | Права | Описание |
|---------|-------|----------|
| **Tier 1** | Read-Only + Draft | Агент только читает данные и готовит черновики. Минимум рисков на этапе тестирования |
| **Tier 2** | Send on Behalf | Агент отправляет сообщения, создаёт события в календаре от имени организации |
| **Tier 3** | Proactive | Полная автономность, выполнение «постоянных поручений» по расписанию (Cron) |

### Управление делегатами:
- В `workspace-delegate` создать детальный `AGENTS.md` с жёсткими границами (Hard Blocks)
- Пример: запрет экспорта финансовых данных, запрет изменения настроек безопасности
- Каждый делегат = отдельный агент со своей областью ответственности

### Sandbox-изоляция делегатов:
- Песочница для каждого делегата — ограничение доступа к файловой системе хоста и сети
- Tool Policy через Gateway — блокировка опасных инструментов на уровне конфигурации
- Пример: делегат для финансов → без `edit` и `browser`

## 14. Кастомные плагины и интеграции

Для специфичных бизнес-интеграций (CRM, ERP и т.д.):

- **`registerProvider`** — регистрация собственных провайдеров
- **`registerHttpRoute`** — добавление HTTP-эндпоинтов
- Преимущества: чистота ядра, модульность, обновления OpenClaw не ломают интеграции
- Интеграции развиваются как отдельные модули/плагины

## 15. CI/CD в закрытом контуре

### Актуальная проблема:
- В репозитории `openclaw-business` падают CI-воркфлоумы (`security-dependency-audit`, `build-artifacts`)
- Сборка документации тоже с ошибками
- Причина: конфигурация нацелена на апстрим `openclaw/openclaw.git` — нужна адаптация

### Решение для контура:
- CI/CD развёрнут внутренний (GitLab CI, Jenkins)
- Зеркало апстрима → внутренний Git → тестирование совместимости перед слиянием
- Каждый апдейт ядра → проверка бизнес-надстроек
